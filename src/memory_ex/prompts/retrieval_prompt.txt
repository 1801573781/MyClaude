## 第一步：任务意图分析

## 第二步：逐条评估
对每条记忆，通过三层过滤判断相关性：

### 层1 — 主题交集
记忆描述的对象与任务涉及的对象是否有交集？
- 无交集 → 1-2分，跳过
- 有交集 → 进入层2

### 层2 — 语义对应
记忆描述的问题/决策/规则，是否与任务要解决的问题在同一层面？
- 完全不同层面（如任务修Bug，记忆讲架构迁移历史）→ 3-4分
- 相邻领域有参考价值但不直接影响 → 5-6分
- 同一层面且可能影响执行决策 → 进入层3

### 层3 — 执行价值
召回这条记忆，会改变当前任务的执行方式吗？能避免什么具体错误？
- 提供背景但不改变决策 → 6-7分
- 可能影响执行方式但不确定 → 7分
- 直接改变执行方式或避免具体错误 → 8-9分
- 记忆直接描述当前任务涉及的代码的已知Bug或约束 → 9-10分

## 常见误判模式（必须避免）
1. **关键词陷阱**：任务和记忆提到相同命令/模块名，但讨论的方面完全不同
   - 任务：/init f 耗时估算不准 → 记忆：/init 命令扫描文件范围 ❌
   - 任务：优化记忆召回评分 → 记忆：记忆提取用字节偏移追踪 ❌
2. **领域泛化**：任务和记忆同属一个大领域，但具体内容无关
   - 任务：file_context_tool 排版修复 → 记忆：CLI /mem 命令迁移 ❌
   - 任务：/init f 耗时估算 → 记忆：/mem show 移除 Layer 0 显示 ❌
3. **因果混淆**：记忆描述了某功能的实现方式，但任务修改的是该功能中完全不同的部分
   - 任务：优化召回评分逻辑 → 记忆：记忆系统数据来源有两个独立通道 ❌

## 标签感知
- [caution]：Bug归纳的通用规则，仅当任务涉及相同代码区域或相似操作模式时才高分
- [架构决策]：需匹配相同模块/功能的设计决策
- [性能基准]：需匹配相同操作的性能数据
- [代码架构]：需匹配相同代码文件/函数的结构信息
- 不要因标签名相同就无条件召回

## 严格约束
- 查询是经过压缩的任务意图摘要，已去除CLI输出噪声
- 仅当记忆信息能直接改变当前任务执行方式时才打 ≥8 分
- "都涉及CLI"、"都涉及统计"不构成相关性
- 必须是同一个函数 / 同一个Bug / 同一个设计决策
- 宁可不召回，不可错召回
